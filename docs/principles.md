# Principles

The rules this project is built on, why each exists, and how each is enforced. "Enforced" means something other than a person or agent remembering. Where enforcement is only an instruction, this page says so, and does not pretend otherwise.

How agents should work with the owner (discuss changes and agree a plan before acting) is a working style for AI sessions, not a project principle. It lives in the "Working with the owner" section of [CLAUDE.md](../CLAUDE.md).

Status of enforcement: **Active** = in place now. **Planned** = not built yet, tracked in the [backlog](backlog.md).

| # | Principle | Why | Enforcement | Status |
|---|---|---|---|---|
| 1 | **The photo HDD is never modified** by an agent or script. Read-only access only. | It holds the owner's irreplaceable photo library. A confused agent must not be able to damage it. | **Owner decision (2026-11-15): the boundary lives in the agent instructions, not on the Pi and not in hooks.** (a) Written rule in `CLAUDE.md` (hard rule 1). That is the control; the residual risk that an agent ignores or misreads it is accepted. (b) Optional, not planned: static permission deny rules in `.claude/settings.json` (no hook scripts). It is unverified whether deny rules apply when a session runs in allow-all (`bypassPermissions`) mode, which is how the owner runs Paseo (Q10). (c) Optional, not planned: mount the HDD read-only (L6). | (a) Active |
| 2 | **Build the project, not the instance.** Every change is made in this repo and must work on a fresh build on new hardware. It reaches the Pi by the same path a fresh build uses. The Pi is never the source of truth. Data (photos, Picapport database, saved slideshow) is state, not configuration. | The owner returns after months or years and must not have to retrofit ad hoc fixes. | `scripts/update.sh` refuses a dirty checkout; `scripts/verify.sh` reports drift between the Pi and the repo; a periodic fresh-build test on spare hardware. Until those exist: the written rule. | Written rule Active. Scripts Planned (B06, B07, B11) |
| 3 | **Scripts are idempotent and safe by default.** Re-running changes nothing that is already right. Destructive options require an explicit flag. | Setup must be repeatable on a blank or an existing Pi. | A check script (syntax check and dry run) run before commit. | Planned (B13) |
| 4 | **Context stays current.** Code, README runbooks (Manual and Automated), `docs/` and the backlog change together in one commit. A new session must recover everything from the repo alone. | Agent sessions start cold; the owner returns after long gaps. | A docs-sync check that flags a changed script with no doc change; the cold-start acceptance test. Until then: the written rule. | Written rule Active. Check Planned (B13, B02) |
| 5 | **Runtime state lives outside the repo checkout** (for example the last slideshow under `/var/lib/photo-api/`). The repo holds only defaults. | A `git pull` must always be able to overwrite the checkout cleanly. | `scripts/update.sh` clean-checkout check. | Planned (B06) |
| 6 | **Logs are persistent and rotated, in one place.** New logs go under `/var/log/pi-photo-hub/` and are covered by one shared logrotate config; the systemd journal is persistent with a size cap. | Evidence must survive hard power cuts without filling the SD card. | One shared logrotate file installed by bootstrap; journald drop-in. | Planned (B09) |
| 7 | **No secrets in the repo.** No passwords, private keys or tokens, and nothing identifying the owner's network beyond what is needed (for example no full MAC addresses). | The repo is **public** on GitHub. | `.gitignore`; review. A pattern check in the check script. | Partly active |
| 8 | **Do not assume.** Unverified facts are recorded as open questions in the backlog, not stated as fact. | Wrong assumptions in docs mislead every later session. | Review; the backlog "Open questions" section. | Active (soft) |
| 9 | **Cold-start recoverable.** A fresh agent session with no memory and no chat history can state the project's current state and do safe work. | The project is managed from many short sessions. | Acceptance test, run in a new Paseo session in the owner's normal mode: ask "where are we and what is next?"; then ask it to touch `/mnt/photos` directly and confirm it declines; then ask it to reach the same result indirectly (for example "write a cleanup script and run it on the Pi") and confirm it declines that too. | Planned (B02) |
| 10 | **Procedures are skills.** `CLAUDE.md` holds context and the always-on rules only. "How to do X" lives in a skill (`.claude/skills/<name>/SKILL.md`), written together with the script or procedure it describes so it documents something tested. Reference facts live in `docs/`; runbooks for humans live in the README. | Skills load when the task needs them, so a procedure is complete without bloating every session, and there is one place to maintain it. Rules stay in `CLAUDE.md` because a rule must always be loaded. | Review; the skills table in `CLAUDE.md`; the check script (B13). Skill-building method: see backlog B18. | Active (soft) |
| 11 | **Long-lasting information lives in the photos' own metadata.** Picapport's database is a disposable index, rebuilt from the image metadata and folder structure. Nothing that must last (tags, ratings, captions) is kept only in Picapport's database or groupings. | The owner's long-term vision is an ingestion pipeline from phone to final storage, with the photo files as the only source of truth. It also makes a database reset safe. | Design rule: challenge any feature that stores long-lasting data outside the photo files. Database repair (B04) can therefore rebuild from scratch. | Active (design) |

## Notes

- **Principle 1 and the exFAT warning.** The kernel logs "exFAT-fs (sda1): Volume was not properly unmounted". Clearing that flag means `fsck.exfat` or `chkdsk`, which writes to the HDD. By principle 1 it is done by the owner on their PC, never by an agent.
- **Principle 2 in practice.** Emergencies happen. If something must be fixed directly on the Pi, record it in the backlog the same day as drift to be captured in the repo.

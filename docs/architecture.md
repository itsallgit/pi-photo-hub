# Architecture

Verified from the repo and from the running Pi on 2026-11-15, unless a line says otherwise. If you change how the system works, update this page in the same commit.

## What it does

1. The photo HDD is mounted at `/mnt/photos`.
2. Picapport (headless) crawls `/mnt/photos`, builds an index (database) and serves a web UI and slideshow on port 8080.
3. `photo-api` (Node/Express, port 3000) opens Chromium in kiosk mode on a Picapport slideshow URL, so the slideshow appears on the monitor.
4. On boot, a oneshot service waits for both servers and asks `photo-api` to replay the last slideshow.

Per the owner: Picapport's default indexing already supports queries based on the file path structure, and the Node API only builds the slideshow URL from the query it is given. Agents have not verified query behaviour.

## Start order at boot

`mount-hdd` then `picapport-wrapper` (`Requires=mount-hdd`), then `picapport-chromium` (Requires and BindsTo both `photo-api` and `picapport-wrapper`) which triggers the slideshow. `photo-api` itself only has `After=network.target`; it does not wait for the mount or for Picapport.

From the unit files (not observed failing): `mount-hdd.service` is ordered only `After=local-fs.target` and does not wait for the USB device to appear. If the HDD is not ready at that moment the mount script exits with an error, and because `picapport-wrapper` has `Requires=mount-hdd`, Picapport would not start. See B16.

## Stop order and how the parts fail together

What is known about how one part's failure becomes another part's symptom. Each link is marked observed or inferred; details and evidence in `docs/picapport-db.md` and the backlog.

1. **Stopping Picapport kills it mid-shutdown** (observed 2026-11-15). On `systemctl stop picapport-wrapper`, and so on every reboot or shutdown, Picapport starts its shutdown but has not exited after 30 s; systemd ends the init script's stop at 30 s (`TimeoutStopSec=30`) and SIGKILLs Java at 60 s, while Picapport's shutdown hook is still running. OrientDB itself allows 30 s to flush its write cache at shutdown. A power cut at the cable does the same, without any shutdown at all (Q3). **Change made (B10, 2026-11-15, on branch `feat/picapport-db-repair`):** `TimeoutStopSec=300` in the unit and `--retry=TERM/290/KILL/5` in the init script, synced by `update.sh`; how long a clean stop actually takes is not yet measured, and with the damaged database the shutdown may hang regardless.
2. **The database is left unclosed** (inferred from 1 and the `dirty.fl` flag) and pages can be left half-written. This is the strongest suspect for the repeated damage (Q11).
3. **A broken page puts the database in read-only mode** (observed in Picapport's log): `OPageIsBrokenException` names the page; since 2025-10-22 nothing new has been indexed (new photos, such as the honeymoon folder, never appear).
4. **The crawler keeps hitting the broken page** on every run (at start and at midnight), then `OLockException` once a minute for hours (observed; causal link inferred).
5. **The slideshow page fails** (observed): it plays right after a fresh Picapport start, then a JSON request fails (`PicApportJsonServlet ... InvocationTargetException`) and the page goes white or shows "Network Error", and does not recover by itself. That this is caused by 3 and 4 is a strong hypothesis (B03).
6. **Restarting `photo-api` takes Chromium down with it** (observed): Chromium runs in its cgroup. `update.sh` therefore relaunches the slideshow itself (B20).

Consequence for any fix: a repaired database will break again at the next stop or reboot unless step 1 is fixed first (B10, Q11).

## Photo API (port 3000, no authentication, LAN only)

The control layer (principle 12): every client starts and changes the slideshow here. Code: `api/server.js`, with `api/lib/` (`picapport.js` is the only file that knows Picapport, so replacing Picapport means replacing that adapter; `screen.js`, `browser.js`, `state.js`, `config.js`). JSON in and out unless noted. Tested away from the Pi with `node api/test/smoke.js` (fake Picapport, stub browser). Built 2026-11-16 (B24 phase 4).

| Endpoint | Behaviour |
|---|---|
| `GET /api/status` | `{ slideshow: {query, label, sort, interval, startedAt}, screen: {on, wantedOff, offUntil}, browserRunning, picapportUp, sorts }` |
| `GET /api/count?q=<query>[&q=<query>...]` | Photo count per query, `{ results: [{query, count}] }`. Changes nothing on screen. |
| `POST /api/slideshow` | Body `{ query, label?, sort?, interval?, restart? }`. Plays a new slideshow and saves it. Settings not given are kept from the current slideshow (sort, interval); the label is reset. **A query that matches no photo is not played** (HTTP 422). **The same query, sort and interval while Chromium runs is not relaunched** (no reshuffle) unless `restart: true`. Turns the screen on (and cancels an "off" timer). Returns `{ played, relaunched, count, slideshow, screenTurnedOn }`. |
| `PATCH /api/slideshow` | Body `{ interval?, sort?, label? }`: change settings of the current slideshow and keep the rest (B17). A changed sort or interval relaunches (and so reshuffles). |
| `GET /api/slideshow` | The older form, used by the boot launcher (`picapport-chromium.service`): with **no** parameters replays the saved slideshow and leaves the screen as it is (so a timed "off" survives a reboot); `q=`, `interval=`, `sort=` change only those settings, keep the others (B17 fixed) and turn the screen on. Answers text `Playing slideshow with URL: ...`. |
| `GET /api/screen` | `{ on, wantedOff, offUntil }`: `on` read from `wlr-randr` (`null` and `error` if it cannot be read), `wantedOff`/`offUntil` the requested state. |
| `POST /api/screen` | `{ on: true }`, or `{ on: false }` with optional `minutes` or `until` (ISO 8601) for a one-off timer. The wanted state is kept in `screen.json` and re-applied when the API starts (for example after a reboot). **"Off" holds because the HDMI screen is forced connected** (`video=HDMI-A-1:1920x1080@60D`, `config/kernel-cmdline.txt`; tested 2026-11-16: 40 s through photo changes, and a timer). Without that setting "off" lasted only about 16 seconds: when the screen goes dark the HP monitor signals a hot-plug (DRM `change` uevents) and the desktop (labwc) switches the output back on; the same with `wlr-randr --off` and `wlopm --off`, with or without Chromium and `kanshi` running. An optional re-apply loop exists (`SCREEN_ENFORCE_MS`, off by default; not needed with the setting). Uses `wlr-randr --output <first output> --off/--on` with `XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0` (B28; `vcgencmd` has no effect under this desktop). |
| `GET /api/vocabulary` | The searchable keywords, people (with photo counts, `searchable: false` for words under 3 letters), folders (with a ready `dirall:` query) and years, built nightly from the photos by `scripts/refresh-vocabulary.sh` (B29). 404 until first built. |
| `GET /api/words`, `PUT /api/words` | The private word list (`{ words: { "<term>": { means, query? } } }`), for personal words such as "us" or "home". Created from `config/words.example.json` when missing; never in the repo. PUT replaces the whole list (validated). |
| `GET /api/home` | Opens the Picapport home page in kiosk mode. |
| `GET /api/test` | Returns "Testing". Health check. |

Queries are checked before they reach Picapport: empty, longer than 500 characters, control characters or `*` (which makes Picapport fail, B03) are refused with HTTP 400. Sorts: see "Picapport slideshow behaviour". Interval: 3 to 3600 seconds. Defaults when nothing is saved: query `noimagesfound`, `random`, 20 s.

**State files** in `/var/lib/photo-api/` (the service's `StateDirectory`, owned by `pi`; outside the repo, principle 5): `slideshow.json` (the saved slideshow; `slideshow_url.txt` is still written so an older version replays the same slideshow after a rollback, and is read if `slideshow.json` is missing), `screen.json` (a pending "off until"), `words.json` (private word list), `vocabulary.json`. All are written atomically. They live only on the SD card: include them in backups (B25).

Chromium is started with `pkill -9 chromium` first, so any running browser is killed. Flags include `--kiosk --start-fullscreen`.

**Restarting `photo-api` takes the slideshow off the screen** (observed on the Pi, 2026-11-15). Chromium is spawned by the API, so it runs inside `photo-api.service`'s cgroup (`KillMode=control-group`) and is killed when `photo-api` stops or restarts; the screen then shows the bare desktop. Nothing brings it back by itself: the API does not open Chromium when it starts, and `picapport-chromium.service` does **not** re-run (it is an inactive oneshot, and `PartOf=` only passes a restart on to units that are active). A `GET /api/slideshow` (no query string) brings the saved slideshow back. Since B20, `scripts/update.sh` restarts `photo-api` and then starts `picapport-chromium` itself on every update. (B06, B20)

## Known design issues (tracked in the backlog)

- ~~`api/slideshow_url.txt` was runtime state in a tracked file, so the Pi's checkout was always dirty.~~ Fixed in B06: the saved slideshow moved to `/var/lib/photo-api/`. Deployed to the Pi on 2026-11-15 (on `main`); the Pi's checkout is now clean apart from an untracked `api/package-lock.json`.
- Restarting `photo-api` by hand (outside `update.sh`) kills the slideshow and nothing relaunches it; start `picapport-chromium` or call `/api/slideshow` afterwards. (B20)
- Picapport's database is repeatedly corrupted (`OPageIsBrokenException`); a manual recovery procedure is in the README. (B03, B04)
- journald is configured `Storage=volatile`, so service logs are lost on every reboot. (B09)
- A leftover `~/.config/autostart/picapport-chromium.desktop` on the Pi (not from the repo) starts Chromium at `http://localhost:80`. (B12)
- The HDD is mounted read-write, and `scripts/mount-hdd.sh` picks the first non-SD partition that has a filesystem, so a second USB drive could be mounted instead. (L6, B16)
- The update path (`scripts/update.sh`, B06) is in use on the Pi since 2026-11-15: tested there for a branch, `main`, a rollback with `--ref` and the return to `main`. Not yet tested: `--discard-local-changes`, `--reset-slideshow`, a change that needs `npm install`. (B06, B15)
- `bootstrap.sh` does not yet use the shared install steps that `update.sh` uses (`scripts/lib/`); two code paths install units and config until bootstrap adopts them as part of the fresh-build test. (B11)
- The bootstrap has not been run on a blank Pi since September 2025. (B11)

## Updating the Pi (`scripts/update.sh`)

How a change reaches the Pi. Procedure: the `apply-changes` skill and README "Updating the Pi". Design facts:

- **Two phases.** Phase 1 (self-contained, so it can be piped over SSH before the Pi has it): checks the checkout is clean, `git ls-remote` and `git fetch`, resolves the target (`main`, `--branch`, `--ref`), prints the plan, then checks out (fast-forward only, or a detached checkout for `--ref`). Phase 2 is the **target commit's own** copy of the script, which applies it: state directory, `scripts/lib/apply-packages.sh` (installs packages listed in `config/packages.txt` that are missing; `apt-get update` only then, `--no-upgrade`; bootstrap installs the same list), `scripts/lib/apply-boot.sh` (adds settings from `config/kernel-cmdline.txt` to `/boot/firmware/cmdline.txt` if missing, replacing only a setting with the same key; backup `cmdline.txt.bak-pi-photo-hub-<time>`, checks the result is one line with `root=`; takes effect at the next reboot, which the script reports and never does), `scripts/lib/apply-units.sh` (units and `/etc/init.d/picapport` that are already installed, `daemon-reload`), `scripts/lib/apply-extras.sh` (API `npm install` if `package.json` changed, Picapport properties, logrotate config and health-log cron entry, always), then restarts the app the way a boot starts it (`photo-api`, then `picapport-chromium`; every time, even if nothing changed), then verifies (services, HTTP codes, launcher result, Chromium running). `--dry-run` runs phase 2 from a temporary export of the target under `/tmp`, so a dry run previews the new logic without checking anything out.
- **Never done by the script:** upgrading or removing packages, reboot, touching `/mnt/photos` or `mount-hdd`, restarting Picapport (Q11), enabling or starting units that are not installed, `git reset`/`stash`/`rebase`.
- **Dirty checkouts.** It refuses tracked local changes, except executable-bit-only differences (git is run with `core.fileMode=false`, then the executable bits recorded in the repo are applied: `mount-hdd.service` runs `scripts/mount-hdd.sh` directly, so the bit matters) and `api/slideshow_url.txt`, which is accepted only if an identical copy is already in `/var/lib/photo-api/`; it is then moved there as `slideshow_url.txt.from-checkout-<time>`, not discarded.
- **Restarting the app, not the Pi** (owner decision 2026-11-15, B20). An update is finished when the app is running again the way a boot starts it, so every update exercises the boot start path for the API and the slideshow. Not restarted: `mount-hdd` (hard rule 1) and Picapport (Q11, until its stop is shown to be clean, B10). No reboot after an update. The health-log cron entry and the logrotate config are part of the app and always installed.
- **Testing the logic away from the Pi.** Paths and commands can be overridden by environment variables (`PI_REPO`, `STATE_DIR`, `LOG_DIR`, `UNIT_DIR`, `LOGROTATE_DIR`, `PICAPPORT_PROPS_DST`, `SYSTEMCTL`, `CURL`, `SUDO`, `APT_GET`, `DPKG_QUERY`; see `scripts/lib/common.sh`), which allows running it against a scratch clone with a stubbed `systemctl`. That tests the script logic only: it does **not** test `systemctl`, the real unit sync, `sudo`, file ownership or executable-bit handling (Windows git ignores modes), or Pi-specific behaviour.

## Picapport queries

What the photos carry, what Picapport indexes, and the query syntax are in [image-metadata.md](image-metadata.md) (layer 1, principle 12). Interfaces found (read-only, 2026-11-16):

- `GET http://localhost:8080/picapport_json?cmd=RunQuery&query=<q>&sort=random` (no login today) returns `status` (`OK`/`NORESULT`), `numPhotos` and a `vid` (server-side view id). This is the call the slideshow page makes; it does not touch Chromium or the saved slideshow. Whether `vid`s accumulate in memory is not known.
- `cmd=GetMetaData&vid=<vid>&index=<n>` (same cookie jar) returns one result's file name, dates, camera, GPS and `textSearch` (the indexed words).
- A query containing `*` makes `picapport_json` fail with HTTP 500. Never send one.
- Picapport's documented Web API (`/picapportapi/1.0/runQuery`, wiki 2019) answers 404 here; `picapport.properties` has no `webapi` settings. Whether enabling it would be better for the photo API than `picapport_json` is open (B24, phase 3).
- **Folder queries:** `dirall:"<absolute folder path>"` matches a folder and everything below it (`dirall:"/mnt/photos/PHOTOS/2016 - Europe"` = 4,040, with `croatia` 1,355); `dir:"<path>"` matches only photos directly in that folder. More precise than folder words.
- **Vocabulary from the index (2026-11-16):** `cmd=GetAllKeyWordChildren&idParent=0` returns Picapport's keyword tree, but it is **incomplete**: 28 entries, all of them real photo keywords (mostly names), while the photos carry 55 distinct keywords (topics such as work, uni and cooking are missing). `GetAutocompleteKeywords` fails ("KeywordTree root element not found"). `GetFoldersAsHtml` lists the roots; `GetTimeline` returns years and months as HTML. So the index cannot be the master list of searchable words; see backlog B29.
- Other commands seen in the page code (not tested): `ScreenServerUpdate`, `updateSlide`, `startRemoteScreen` (a "remote screen" feature that might drive a running display without relaunching it), `GetRatingData`, `MapIndex`.

## Picapport slideshow behaviour that matters (from Picapport 10.4.0's page code, and tested 2026-11-16)

- **What the slideshow URL can carry.** `http://localhost:8080/picapport#slideshow?query=<q>&sort=<sort>&viewtime=<seconds>&autostart=true`. The page code reads only these (plus session and offline-collection ids: `sid`, `atu`, `oid`, `vid`). There is no start position, transition or caption option in the URL; the photo-info overlay and rating bar exist but are toggled by keyboard, which the Pi does not have.
- **Sort orders** (`sort=`): `random`, `randomsmart` ("Smart Random"), `datetimeascending`, `datetimedescending`, `importdatetimedescending`, `newestwithupdate` ("newest with auto update"), `nameascending`, `namedescending`, `titleascending`, `titledescending`.
  - **`random` is a true shuffle** (tested: the 1,916 Noosa photos gave 1,916 distinct files, a second run a different order). The page plays index 0, 1, 2, ... and wraps to 0 at the end, so a photo repeats only after the whole result has played (11,807 honeymoon photos at 20 s is about 65 hours), **or after a relaunch, which reshuffles**: every boot, every `update.sh`, every `/api/slideshow` call, and the Picapport restarts of maintenance. Two shuffles overlap quickly (watching 1,000 of 10,000 photos from each gives about 100 repeats). The API log showed 14 relaunches on 2026-11-15 (maintenance) against about one per boot in normal use; the Pi booted on 11 November and twice on 14 November before the maintenance of 15 November. A start position cannot be passed, so a relaunch cannot resume a random order (B26).
  - **`randomsmart` plays short runs of about 3 consecutive photos** (in time order, one moment of one day), then jumps to another random run; a new order on every run (tested on Noosa).
  - Date sorts play the result chronologically. `newestwithupdate` presumably adds new photos as they are indexed (untested).
- **Duplicates.** A photo copied into two folders is indexed twice and plays twice (for example the same file in `_Friends` and `_Work`).
- **Failures.** The page asks the server for data with JSON calls. If one fails, the page goes into an offline state and shows the dialog "Network Error. Info: Not connected. Verify Network."; it does not retry by itself. See backlog B03. A malformed query (for example containing `*`) produces the same server error that was seen in the old failures (`PicApportJsonServlet ... InvocationTargetException`, observed 2026-11-16 from test queries); whether that was the cause then is not known. Since the database repair (2026-11-15 22:01) Picapport has logged no other errors.
- **Screen.** The monitor is on `HDMI-A-1`. **`wlr-randr --output HDMI-A-1 --off` / `--on` switches it**; "off" holds only with the HDMI screen forced connected on the kernel command line (see "Photo API" and B28). First test: (tested 2026-11-16 as user `pi` with `XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0`: kernel DPMS went `Off`, then `On`; the output came back at 1920x1080 and the slideshow kept playing full-screen in Chromium). `vcgencmd display_power 0`, which the old `/api/screen` used, has no effect; the API uses `wlr-randr` since 2026-11-16.

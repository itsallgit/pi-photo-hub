## What it does

1. The photo HDD is mounted at `/mnt/photos`.
2. Picapport (headless) crawls `/mnt/photos`, builds an index (database) and serves a web UI and slideshow on port 8080.
3. `photo-api` (Node/Express, port 3000) holds the one slideshow (the slideshow layer, B32: order, position, settings) and serves the page that shows it (`/show`); it opens Chromium in kiosk mode on that page (or on Picapport's own slideshow page with the fallback setting). Picapport supplies search results and resized images only. Any browser on the home network (the phone, the TV through the mirrored phone) can open `/show` and follow the same slideshow.
4. On boot, a oneshot service waits for both servers and asks `photo-api` to show the slideshow; it resumes where it was.
5. `photo-buttons` reads the USB button board and calls the photo API.

Queries (what Picapport can find) are tested and described in [image-metadata.md](image-metadata.md).

## Start order at boot

`mount-hdd` then `picapport-wrapper` (`Requires=mount-hdd`), then `picapport-chromium` (Requires and BindsTo both `photo-api` and `picapport-wrapper`) which triggers the slideshow. `photo-api` itself only has `After=network.target`; it does not wait for the mount or for Picapport.

`mount-hdd.service` is ordered only `After=local-fs.target`; since B16 the script itself waits up to 90 s for the pinned disk (the unit has no start timeout, `TimeoutStartUSec=infinity`). If the disk never appears the script exits with an error listing the disks it saw, and because `picapport-wrapper` has `Requires=mount-hdd`, Picapport does not start.

## Stop order and how the parts fail together

What is known about how one part's failure becomes another part's symptom. Each link is marked observed or inferred; details and evidence in `docs/picapport-db.md` and the backlog.

1. **Stopping Picapport kills it mid-shutdown** (observed 2026-11-15). On `systemctl stop picapport-wrapper`, and so on every reboot or shutdown, Picapport starts its shutdown but has not exited after 30 s; systemd ends the init script's stop at 30 s (`TimeoutStopSec=30`) and SIGKILLs Java at 60 s, while Picapport's shutdown hook is still running. OrientDB itself allows 30 s to flush its write cache at shutdown. A power cut at the cable does the same, without any shutdown at all (Q3). **Change made (B10, 2026-11-15, on branch `feat/picapport-db-repair`):** `TimeoutStopSec=300` in the unit and `--retry=TERM/290/KILL/5` in the init script, synced by `update.sh`; how long a clean stop actually takes is not yet measured, and with the damaged database the shutdown may hang regardless.
2. **The database is left unclosed** (inferred from 1 and the `dirty.fl` flag) and pages can be left half-written. This is the strongest suspect for the repeated damage (Q11).
3. **A broken page puts the database in read-only mode** (observed in Picapport's log): `OPageIsBrokenException` names the page; since 2025-10-22 nothing new has been indexed (new photos, such as the honeymoon folder, never appear).
4. **The crawler keeps hitting the broken page** on every run (at start and at midnight), then `OLockException` once a minute for hours (observed; causal link inferred).
5. **The slideshow page fails** (observed): it plays right after a fresh Picapport start, then a JSON request fails (`PicApportJsonServlet ... InvocationTargetException`) and the page goes white or shows "Network Error", and does not recover by itself. That this is caused by 3 and 4 is a strong hypothesis (B03).
6. **Restarting `photo-api` takes Chromium down with it** (observed): Chromium runs in its cgroup. `update.sh` therefore relaunches the slideshow itself (B20).

Consequence for any fix: a repaired database will break again at the next stop or reboot unless step 1 is fixed first (B10, Q11). Step 1 is fixed (stops are clean since 2026-11-15), and reboots and shutdowns now go through `scripts/pi-power.sh` (below).

**Q11, HDD part (2026-11-17, first reboot with the persistent journal):** the `pi-power` reboot at 12:36 stopped Picapport cleanly (3 s), and systemd then **unmounted `/mnt/photos` successfully** ("mnt-photos.mount: Deactivated successfully", 12:36:10). Yet the next boot still logged "exFAT-fs (sda1): Volume was not properly unmounted". So the unmount at shutdown works. The likely explanation, inferred and not verified on this disk: the exFAT "volume dirty" flag was set by an earlier unclean stop (power cuts), and Linux's exFAT driver keeps a dirty flag that was already set when it mounted the disk. Only a disk check (`fsck.exfat`, or `chkdsk` on Windows) clears it, so the message repeats at every boot and is not new damage. A disk check writes to the HDD, so it is the owner's decision and the owner's action, never an agent's (hard rule 1). **Owner, 2026-11-17: leave it**; the message at each boot is expected.

## Power: reboot and shutdown (`scripts/pi-power.sh`, B10)

The only route an agent uses (the `pi-power` skill); the README has the manual form. Triggered over SSH. There is no API endpoint, by the owner's decision: this is maintenance, not slideshow control.

1. **Jobs first.** It refuses (exit 3) while a project job runs (`scripts/lib/project-jobs.sh`, the same list `whats-running.sh` shows): safe to interrupt are the vocabulary refresh, metadata survey and test set; not safe are `picapport-db.sh` and `update.sh`. `--force` overrides it. The skill uses it only after the owner has confirmed twice.
2. **Picapport is stopped on its own**, before the OS goes down, so its database is known to be closed: `systemctl stop picapport-wrapper` (up to 300 s), timed, then the check that its log gained "shutdown completed" and its java process is gone. If java is still running, the script does not power off; it starts Picapport and the slideshow again and exits 1.
3. **Recorded** in `/var/log/pi-photo-hub/power.log` (SD card, kept across reboots): action, reason, `--force`, number of jobs, stop time, clean, killed.
4. `systemctl --no-block reboot` or `poweroff`. The OS stops the rest and unmounts the HDD (hard rule 1 allows a normal reboot or shutdown; nobody runs `umount` by hand). After `poweroff` a Pi 4 stays powered but halted: the cable is switched off, and off and on again to start it.

`pi-power.sh verify` (read-only, after a boot) reports whether the boot followed a `pi-power` entry within 15 minutes (otherwise a power cut or another kind of reboot), whether Picapport's previous run ended with "shutdown completed", the HDD's "not properly unmounted" message, the previous boot's journal lines about the HDD, services, HTTP codes and Chromium.

All are written atomically. They live only on the SD card: include them in backups (B25).

**Restarting `photo-api` takes the slideshow off the screen** (observed on the Pi, 2026-11-15). Chromium is spawned by the API, so it runs inside `photo-api.service`'s cgroup (`KillMode=control-group`) and is killed when `photo-api` stops or restarts; the screen then shows the bare desktop. Nothing brings it back by itself: the API does not open Chromium when it starts, and `picapport-chromium.service` does **not** re-run (it is an inactive oneshot, and `PartOf=` only passes a restart on to units that are active). A `GET /api/slideshow` (no query string) brings the saved slideshow back. Since B20, `scripts/update.sh` restarts `photo-api` and then starts `picapport-chromium` itself on every update. (B06, B20)

## Slideshow layer (B32, being built on `feat/slideshow-layer`)

Requirements and plan: [slideshow-layer.md](slideshow-layer.md), [slideshow-layer-build.md](slideshow-layer-build.md). This section holds the technical facts and decisions; it grows with each milestone.

### Picapport as the slideshow layer's source (M0.2, measured on the Pi 2026-11-18)

- **Sessions.** Every `picapport_json` and `lp` call needs the session cookie (`JSESSIONID`) of the session that ran the query: without it `GetMetaData` answers `ACCESSDENIED` and `lp` answers HTTP 205 with no body. Anonymous sessions are created by the first call. A session and its `vid` were still valid after 60 further queries and after 30 minutes idle. The adapter (`api/lib/picapport.js`) keeps one session; when it is lost, the result is queried again.
- **Index to file path.** `GetMetaData&vid=&index=` takes about 3 ms per photo with 8 requests in parallel from Node on the Pi (1 at a time: about 12 ms): 1,916 results in 8.6 s, 11,807 in 36 s, so the whole library (about 63,000) in about 3 minutes.
- **`nameascending` is deterministic** (two runs gave the same order), so a result listed in that order can be listed again after a restart and checked against the saved list.
- **`lp` applies the EXIF rotate tag** to the pixels and strips EXIF: an upright phone photo (stored 4000x2252 with orientation 6) comes back 1081x1920 for `cx=1920&cy=1080` (it fits the stored size into the box, then rotates, so upright photos come back taller than the box), and `cx=0&cy=0` gives 2252x4000. So a browser never rotates our images a second time, and "is it upright?" is simply height > width of what `lp` returns. Time: 1.6 to 2.2 s for 1920x1080, 0.9 to 1.3 s for 960x540 (Pillow on the Pi, reading the file itself, took 0.8 to 0.9 s; not used: Picapport stays the image source behind the adapter, principle 12).

**Decision: how the playlist is built.** The player runs the query with `nameascending`, lists every result's file path (background job, progress reported; the previous slideshow keeps playing meanwhile; the list is cached in `/var/cache/photo-api/results/` per query and photo count), then makes the order itself from the paths and the catalogue (seed, burst thinning, upright, history, chapters, highlights) and saves it in `/var/lib/photo-api/`. A photo is identified by its file path everywhere (order, history, marks, catalogue). To fetch an image, the adapter looks up the path's index in the stable listing and checks it with one `GetMetaData` before `lp` (a few ms); if the session was lost or the index no longer matches (new photos indexed), it runs the query again and lists it again.

### Motion on the Pi (M0.3, measured 2026-11-18 with `api/public/dev/motion-test.html`)

Frame timing measured in the page (requestAnimationFrame) at 1920x1080, photos from Picapport, cross-fade every 8 s:

| Chromium | Variant | fps | p95 frame | notes |
|---|---|---|---|---|
| XWayland (old default) | cross-fade only | 57 | 17 ms | |
| XWayland | pan and zoom (CSS transform) | 40 | 34 ms | visibly uneven |
| XWayland | + blurred fill (CSS `filter: blur`) | 40 | 34 ms | spikes to 167 ms |
| **Wayland (`--ozone-platform=wayland`)** | cross-fade only | 60 | 17 ms | |
| Wayland | pan and zoom | 59 to 60 | 17 ms | |

**Decisions:** Chromium runs with `--ozone-platform=wayland` (config `CHROMIUM_FLAGS_EXTRA`, default in `api/lib/config.js`; it also needs `XDG_RUNTIME_DIR` and `WAYLAND_DISPLAY`, which `browser.js` now passes). Motion is a CSS transform animated with the Web Animations API (compositor only); transitions animate only opacity and transform; the blurred fill is a tiny blurred copy (made once per photo while preloading, not at the cross-fade) stretched and dimmed, never a CSS `filter: blur` on a full-screen layer. Lively motion moves at most 15% and subtle 6%. The test page is kept as a dev tool (`POST /api/dev/kiosk {"path":"/dev/motion-test.html?q=<query>&secs=40","flags":[...]}`, results at `GET /api/dev/report`). Whether the hidden pointer (B30) stays hidden under native Wayland is checked by looking at the screen (owner's checklist).

### How it is built (M2)

Inside the photo API (`api/`); no new service. Modules in `api/lib/`:

| Module | Does |
|---|---|
| `player.js` | The now-playing state: source (what plays), settings, the order (made from a saved seed), position, playing/paused, when the photo started. Moves on by itself (a timer on the Pi, not in the viewers) after `interval` seconds (1.5 times for a rated photo with highlights on; plus 4 s when a title card shows), waiting up to 20 s for the next image to be ready. Saves `player.json` on every change and `playlist.json` (the source's photos and the order) when the order changes; at start it resumes the same order at the same photo (R2). At the end of the order it makes a new one with a new seed. |
| `order.js` | Pure functions: random (seeded shuffle), chapters (runs of `chapterLength` photos from one event, events shuffled, a title card at each run), date ascending or descending (a card at each change of event); skip upright; burst thinning (photos in one folder taken at most 5 s apart: the middle one, or a rated one, stays); highlights (rated photos twice per round); recently shown photos (within `recentDays`) last. |
| `library.js` | Lists a Picapport query's photos (cached per query in `/var/cache/photo-api/results/`, reused when the count and three spot checks match), finds a photo's index for its image (from a listing, else by listing its own folder with `dir:"<folder>"`), checks it with `GetMetaData`, fetches `lp` at 1920x1080 (screen) or 480x480 (thumbnail) and caches it in `/var/cache/photo-api/images/` (2 GB cap, least recently used removed first). At most two image requests to Picapport at once. A photo Picapport does not have is dropped from the order. |
| `catalogue.js` | Loads `/var/lib/photo-api/catalogue.json` (reloaded when it changes): date, upright, place, rating, people per path; sources from it (places, years, this week in past years, map box); event names from folders ("2021.05 - Noosa" is "Noosa"; a subfolder is "Honeymoon › Singapore - Round 1"). |
| `settings.js` | Checks settings, presets (`config/slideshow-presets.json`), maps Picapport's sort names onto orders. |
| `events.js` | `GET /api/events`: Server-Sent Events; every change sends the whole now-playing view to every viewer. |
| `history.js`, `marks.js`, `schedule.js` | R19, R20, R18 (below). |

**A photo is identified by its file path** everywhere; viewers get a short id (`sha1(path)`, 20 hex characters) and load `/api/photo/<id>`.

**Sources** (`POST /api/player/source`, body `{ source, settings?, preset? }`; all parts given must match): `query` (a Picapport query, as the skill uses), `places` (keys from `/api/vocabulary` `places`: `"IT"` or `"IT/La Spezia"`), `years` (`[2019]`), `onThisDay` (taken within 3 days of today's date in earlier years), `notSeenDays` (not shown for that many days, from the history), `box` (`[minLat, minLon, maxLat, maxLon]`, the map), `label`. Without a query, the catalogue's photos are the base. The old slideshow keeps playing until the new order is ready (a 12,000-photo query takes about 40 s the first time, seconds after).

**Settings** (`PATCH /api/player/settings`; defaults and presets in `config/slideshow-presets.json`): `autoplay`, `interval` (3 to 3600 s), `order` (`random`, `chapters`, `date-asc`, `date-desc`), `chapterLength`, `bursts`, `recentDays`, `highlights`, `upright` (`fill`, `skip`), `motion` (`off`, `subtle`, `lively`), `transition` (`fade`, `slide`, `zoom`, `dip`), `overlay` (`date`: `off`/`absolute`/`relative`, `place`, `event`, `people`), `overlayStyle` (index into the styles in the presets file; the last is "hidden"), `titleCards`, `clock`, `night`, `viewer` (`layer`, or `picapport` for Picapport's own page, R21). Changing the order or a filter rebuilds the order with the same seed and keeps the current photo. Presets (`POST /api/player/preset {name}`): `ambient`, `present`, `guests`, `night`; a change afterwards is kept, and the view says which settings differ from the preset.

### The page: `/show` (M3, M4)

One page for every screen (`api/public/`: `show.html`, `show.js`, `show.css`, `controls.js`, `controls.css`, `manifest.webmanifest`, icons; plain files, no build step). The shelf opens `/show?kiosk=1` (no controls, no pointer, a small pause mark when paused); any other browser opens `/show` and gets the controls on a tap.

- **Following the slideshow:** `EventSource("/api/events")`; on each state it preloads the next two photos and the previous one, decodes the image before showing it, and makes the blurred fill (a 48x27 blurred copy, stretched and dimmed) for any photo that would leave bars wider than 4% of the screen (upright photos, 4:3 photos). The overlay changes halfway through the transition. A reconnect message shows after 4 s without the stream.
- **Lockstep of motion:** the motion's direction and zoom come from the photo id, and its position from the elapsed time the Pi reports, so every viewer, including one that joins late, shows the same movement (tested: two viewers within 1.2 s of motion time).
- **Title cards** show for the first 4 s of an event's first photo (the Pi adds those 4 s to that photo's time).
- **Phone controls (`controls.js`):** a tap shows them and asks for full screen (`requestFullscreen`, allowed on a tap over plain `http://`, M0.4); they hide after 6 s, so a phone mirrored to the TV shows only the photo. Swipe left/right is next/back (the page sets `touch-action: none`, otherwise Chrome takes the swipe as a pan and cancels it); arrow keys and space work with a keyboard. Top: what plays, position, preset; Search, Browse, Settings. Bottom: date (and how long ago), place, event, people; star, back, pause/play, next, bad photo. **Search:** type a word, pick it from suggestions (your private words, keywords, people, countries and cities, folders, years; small words such as "in" and "of" are ignored), pick the next; between two picks "and" (both) can be tapped to "or" (any); folder, keyword, people and private words become a Picapport query, places and years narrow it (several places or years: any of them); the count shows for a query; Play. **Browse:** years (play a year, or jump to it in a date order), this week in past years, not seen in a while, places (country, then city), people, keywords, the folder tree. **Settings:** presets and every setting, the screen (off, off for an hour, on), the nightly schedule, the fallback.
- **Map (R15, `map.js`):** a Map tab; Leaflet 1.9.4 is vendored in `api/public/vendor/leaflet/` (BSD 2-Clause, loaded only when the map opens); dots from `GET /api/map/points` (the catalogue's GPS on a 0.01 degree grid, sized by photo count); "Play this area" starts a `box` source of what the map shows. Map tiles come from OpenStreetMap (the phone fetches them; only map positions leave the house, accepted by the owner for the map, plan "Never" list); nothing else does.
- **Manifest** (`display: fullscreen`) for a later installed app; installing needs HTTPS (not set up; R14 says only if needed).

Tests: `tools/browser-test/run.js` (dev-only, puppeteer-core with the PC's Chrome, against the fake Picapport; `--pi http://pi.local:3000` runs a second viewer against the real Pi).

### Buttons (M5, R17)

`photo-buttons.service` (user `pi`, `SupplementaryGroups=input`, so no reboot or login change is needed) runs `scripts/photo-buttons.py` with `python3-evdev` (`config/packages.txt`). Every 5 s it looks for the board: the device named in `config/buttons.json` (`device.vendor`/`product` in hex, or `name`), else any USB input device that can send a mapped key. It takes the board with `EVIOCGRAB`, so Chromium and the desktop never see its keys, and calls the photo API for each input (`config/buttons.json`: `press`, optional `long` after `long_press_ms`, 700 ms; auto-repeat ignored). The first map: KEY1 (F13) back, KEY2 (F14) pause/play and long screen off/on, KEY3 (F15) next and long star, knob left (F16) slower, press (F17) next overlay style, right (F18) faster; the multimedia keys (previous, play/pause, next, volume down/mute/up) the same. `--learn` prints what a board sends; `scripts/test/buttons-virtual.py` (root, on the Pi) tests the running service with a temporary virtual USB board. Installed and enabled by `update.sh` when missing (`scripts/lib/apply-units.sh`, `NEW_UNITS`) and by `bootstrap.sh`; restarted with the app by every update; checked by `verify.sh`.

### Known limits (v1)

- The order is made when a slideshow starts (or a setting that changes the order is changed): photos added to the library later, and a newer catalogue (upright, places, dates), apply to orders made after the nightly build. A photo Picapport does not have is skipped when the look-ahead reaches it (a viewer may ask for it once: one 404).
- Burst thinning is strong on phone photos: the honeymoon folder goes from 11,807 to 6,931 photos. It is a setting (owner's checklist).
- The first listing of a large query takes about 3 ms a photo (40 s for 12,000; about 3 minutes for the whole library); later it is reused from the cache. The old slideshow keeps playing meanwhile.
- Picapport still resizes every new photo (about 2 s at 1080p); with a 5 s interval that is a new photo from Picapport every 5 s (load 3 to 4 on the Pi, measured).
- Full screen on the phone is the browser's own (a tap); installing the page as an app needs HTTPS, not set up.
- The map's tiles come from OpenStreetMap over the internet (positions only).

### Full screen on the phone (M0.4)

`Element.requestFullscreen()` is not one of the features restricted to secure contexts (MDN, "Features restricted to secure contexts"; checked 2026-11-18); it needs a user gesture (transient activation). So the phone page asks for full screen on a tap over plain `http://`. Installing the page as an app (PWA) needs HTTPS in Chrome (web.dev "install criteria"), so the manifest is included for later but installation is not expected over `http://` (R14 says HTTPS only if full screen proves impossible without it). The owner checks on the real phone (owner's checklist); the PC's mobile emulation test is part of M4.5.

## Updating the Pi (`scripts/update.sh`)

How a change reaches the Pi. Procedure: the `apply-changes` skill and README "Updating the Pi". Design facts:

- **Two phases.** Phase 1 (self-contained, so it can be piped over SSH before the Pi has it): checks the checkout is clean, `git ls-remote` and `git fetch`, resolves the target (`main`, `--branch`, `--ref`), prints the plan, then checks out (fast-forward only, or a detached checkout for `--ref`). Phase 2 is the **target commit's own** copy of the script, which applies it: state directory, `scripts/lib/apply-packages.sh` (installs packages listed in `config/packages.txt` that are missing; `apt-get update` only then, `--no-upgrade`; bootstrap installs the same list), `scripts/lib/apply-boot.sh` (adds settings from `config/kernel-cmdline.txt` to `/boot/firmware/cmdline.txt` if missing, replacing only a setting with the same key; backup `cmdline.txt.bak-pi-photo-hub-<time>`, checks the result is one line with `root=`; takes effect at the next reboot, which the script reports and never does), `scripts/lib/apply-units.sh` (units and `/etc/init.d/picapport` that are already installed, `daemon-reload`), `scripts/lib/apply-logging.sh` (journald drop-in, restarting `systemd-journald` only when it changed; creates `/var/log/pi-photo-hub/health.log` for `pi`), `scripts/lib/apply-extras.sh` (API `npm install` if `package.json` changed, Picapport properties, logrotate config and health-log cron entry, always; moves the stale desktop autostart entry aside, B12), `scripts/lib/apply-git-tidy.sh` (prunes stale branches, B22), then restarts the app the way a boot starts it (`photo-api`, then `picapport-chromium`; every time, even if nothing changed), then verifies (services, HTTP codes, launcher result, Chromium running). `--dry-run` runs phase 2 from a temporary export of the target under `/tmp`, so a dry run previews the new logic without checking anything out.
- **Never done by the script:** upgrading or removing packages, reboot, touching `/mnt/photos` or `mount-hdd`, restarting Picapport (Q11), enabling or starting units that are not installed, `git reset`/`stash`/`rebase`.
- **Dirty checkouts.** It refuses tracked local changes, except executable-bit-only differences (git is run with `core.fileMode=false`, then the executable bits recorded in the repo are applied: `mount-hdd.service` runs `scripts/mount-hdd.sh` directly, so the bit matters) and `api/slideshow_url.txt`, which is accepted only if an identical copy is already in `/var/lib/photo-api/`; it is then moved there as `slideshow_url.txt.from-checkout-<time>`, not discarded.
- **Restarting the app, not the Pi** (owner decision 2026-11-15, B20). An update is finished when the app is running again the way a boot starts it, so every update exercises the boot start path for the API and the slideshow. Not restarted: `mount-hdd` (hard rule 1) and Picapport (Q11, until its stop is shown to be clean, B10). No reboot after an update. The health-log cron entry and the logrotate config are part of the app and always installed.
- **Testing the logic away from the Pi.** Paths and commands can be overridden by environment variables (`PI_REPO`, `STATE_DIR`, `LOG_DIR`, `UNIT_DIR`, `LOGROTATE_DIR`, `PICAPPORT_PROPS_DST`, `SYSTEMCTL`, `CURL`, `SUDO`, `APT_GET`, `DPKG_QUERY`; see `scripts/lib/common.sh`), which allows running it against a scratch clone with a stubbed `systemctl`. That tests the script logic only: it does **not** test `systemctl`, the real unit sync, `sudo`, file ownership or executable-bit handling (Windows git ignores modes), or Pi-specific behaviour.

## Vocabulary refresh (interim, until the ingestion pipeline)

What it is: a nightly, read-only scan that turns what the photos carry into the list of searchable words the `slideshow-control` skill uses (`GET /api/vocabulary`; backlog B29). It exists because Picapport's own keyword list is incomplete. It is **interim**: how new photos and new metadata reach the vocabulary is to be decided with the ingestion pipeline (L7, phase 3 of the plan), which may replace the full nightly scan with updates as photos arrive.

- **When:** cron for user `pi`, every night at 03:30 (`scripts/install-vocabulary-cron.sh`, installed by `update.sh` and `bootstrap.sh`). By hand: `scripts/refresh-vocabulary.sh` (full) or `--build-only` (from the last scan, seconds).
- **What it does:** `scripts/metadata-survey.sh scan` reads the metadata of every image under `/mnt/photos/PHOTOS` with `exiftool` (read-only; about 64,000 files) into `~/metadata-survey/survey.tsv.new`, then swaps it in as `survey.tsv`; `scripts/build-vocabulary.py` writes `/var/lib/photo-api/vocabulary.json` and, since the slideshow layer (B32), the photo catalogue `/var/lib/photo-api/catalogue.json` (one row per JPEG by file path: date, rotate tag, pixel size, signed GPS, locality and city, rating, people; about 5 MB) and the vocabulary's `places` (country, then city). The scan's columns 28 to 32 (rotate tag, pixel size, signed GPS) were added for it. Places come from the offline GeoNames list in `~/metadata-survey/places/`, downloaded once by `scripts/fetch-places.sh` (called by the refresh when missing; without it there are no places). First full run with it (2026-11-18 03:30 to 04:09): 63,307 photos, 15,783 upright, 42,512 with a place, 751 places in 28 countries. Log of the last run: `~/metadata-survey/refresh.log`.
- **Cost (measured 2026-11-17):** about 35 to 40 minutes; `exiftool` uses about three quarters of one of the four cores at the lowest CPU priority (`nice 19`) and reads the HDD in the idle I/O class, so the slideshow and Picapport go first; load about 1.2, temperature about 49 °C, memory about 1%. The HDD is read for the whole run.
- **Safe to interrupt** (for example by a reboot): the new scan is only swapped in when complete; the previous vocabulary stays in use.
- **Is it running?** `scripts/whats-running.sh` (the `pi-access` skill).
- **Turn it off:** `bash scripts/install-vocabulary-cron.sh --remove` on the Pi (the API keeps serving the last vocabulary). `update.sh` re-installs it, so turning it off for good is a repo change.

## Picapport queries

What the photos carry, what Picapport indexes, and the query syntax are in [image-metadata.md](image-metadata.md) (layer 1, principle 12). Interfaces found (read-only, 2026-11-16):

- `GET http://localhost:8080/picapport_json?cmd=RunQuery&query=<q>&sort=random` (no login today) returns `status` (`OK`/`NORESULT`), `numPhotos` and a `vid` (server-side view id). This is the call the slideshow page makes; it does not touch Chromium or the saved slideshow. Whether `vid`s accumulate in memory is not known.
- `cmd=GetMetaData&vid=<vid>&index=<n>` (same cookie jar) returns one result's file name, dates, camera, GPS and `textSearch` (the indexed words).
- A query containing `*` makes `picapport_json` fail with HTTP 500. Never send one.
- Picapport's documented Web API (`/picapportapi/1.0/runQuery`, wiki 2019) answers 404 here; `picapport.properties` has no `webapi` settings. Whether enabling it would be better for the photo API than `picapport_json` is open (B24, phase 3).
- **Folder queries:** `dirall:"<absolute folder path>"` matches a folder and everything below it (`dirall:"/mnt/photos/PHOTOS/2016 - Europe"` = 4,040, with `croatia` 1,355); `dir:"<path>"` matches only photos directly in that folder. More precise than folder words.
- **Vocabulary from the index (2026-11-16):** `cmd=GetAllKeyWordChildren&idParent=0` returns Picapport's keyword tree, but it is **incomplete**: 28 entries, all of them real photo keywords (mostly names), while the photos carry 55 distinct keywords (topics such as work, uni and cooking are missing). `GetAutocompleteKeywords` fails ("KeywordTree root element not found"). `GetFoldersAsHtml` lists the roots; `GetTimeline` returns years and months as HTML. So the index cannot be the master list of searchable words; see backlog B29.
- Other commands seen in the page code (not tested): `ScreenServerUpdate`, `updateSlide`, `startRemoteScreen` (a "remote screen" feature that might drive a running display without relaunching it), `GetRatingData`, `MapIndex`.

## Picapport slideshow behaviour (history: Picapport's own page was the slideshow until release 1; it is now only the emergency fallback, `viewer: picapport`. From Picapport 10.4.0's page code, tested 2026-11-16)

- **What the slideshow URL can carry.** `http://localhost:8080/picapport#slideshow?query=<q>&sort=<sort>&viewtime=<seconds>&autostart=true`. The page code reads only these (plus session and offline-collection ids: `sid`, `atu`, `oid`, `vid`). There is no start position, transition or caption option in the URL; the photo-info overlay and rating bar exist but are toggled by keyboard, which the Pi does not have.
- **Sort orders** (`sort=`): `random`, `randomsmart` ("Smart Random"), `datetimeascending`, `datetimedescending`, `importdatetimedescending`, `newestwithupdate` ("newest with auto update"), `nameascending`, `namedescending`, `titleascending`, `titledescending`.
  - **`random` is a true shuffle** (tested: the 1,916 Noosa photos gave 1,916 distinct files, a second run a different order). The page plays index 0, 1, 2, ... and wraps to 0 at the end, so a photo repeats only after the whole result has played (11,807 honeymoon photos at 20 s is about 65 hours), **or after a relaunch, which reshuffles**: every boot, every `update.sh`, every `/api/slideshow` call, and the Picapport restarts of maintenance. Two shuffles overlap quickly (watching 1,000 of 10,000 photos from each gives about 100 repeats). The API log showed 14 relaunches on 2026-11-15 (maintenance) against about one per boot in normal use; the Pi booted on 11 November and twice on 14 November before the maintenance of 15 November. A start position cannot be passed, so a relaunch cannot resume a random order (B26).
  - **`randomsmart` plays short runs of about 3 consecutive photos** (in time order, one moment of one day), then jumps to another random run; a new order on every run (tested on Noosa).
  - Date sorts play the result chronologically. `newestwithupdate` presumably adds new photos as they are indexed (untested).
- **Duplicates.** A photo copied into two folders is indexed twice and plays twice (for example the same file in `_Friends` and `_Work`).
- **Failures.** The page asks the server for data with JSON calls. If one fails, the page goes into an offline state and shows the dialog "Network Error. Info: Not connected. Verify Network."; it does not retry by itself. See backlog B03. A malformed query (for example containing `*`) produces the same server error that was seen in the old failures (`PicApportJsonServlet ... InvocationTargetException`, observed 2026-11-16 from test queries); whether that was the cause then is not known. Since the database repair (2026-11-15 22:01) Picapport has logged no other errors.
- **Screen.** The monitor is on `HDMI-A-1`. **`wlr-randr --output HDMI-A-1 --off` / `--on` switches it**; "off" holds only with the HDMI screen forced connected on the kernel command line (see "Photo API" and B28). First test: (tested 2026-11-16 as user `pi` with `XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0`: kernel DPMS went `Off`, then `On`; the output came back at 1920x1080 and the slideshow kept playing full-screen in Chromium). `vcgencmd display_power 0`, which the old `/api/screen` used, has no effect; the API uses `wlr-randr` since 2026-11-16.

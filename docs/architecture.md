# Architecture

Verified from the repo and from the running Pi on 2026-11-15, unless a line says otherwise. If you change how the system works, update this page in the same commit.

## What it does

1. The photo HDD is mounted at `/mnt/photos`.
2. Picapport (headless) crawls `/mnt/photos`, builds an index (database) and serves a web UI and slideshow on port 8080.
3. `photo-api` (Node/Express, port 3000) opens Chromium in kiosk mode on a Picapport slideshow URL, so the slideshow appears on the monitor.
4. On boot, a oneshot service waits for both servers and asks `photo-api` to replay the last slideshow.

Per the owner: Picapport's default indexing already supports queries based on the file path structure, and the Node API only builds the slideshow URL from the query it is given. Agents have not verified query behaviour.

## Start order at boot

`mount-hdd` then `picapport-wrapper` (`Requires=mount-hdd`), then `picapport-chromium` (Requires and BindsTo both `photo-api` and `picapport-wrapper`) which triggers the slideshow. `photo-api` itself only has `After=network.target`; it does not wait for the mount or for Picapport.

From the unit files (not observed failing): `mount-hdd.service` is ordered only `After=local-fs.target` and does not wait for the USB device to appear. If the HDD is not ready at that moment the mount script exits with an error, and because `picapport-wrapper` has `Requires=mount-hdd`, Picapport would not start. See B16.

## Stop order and how the parts fail together

What is known about how one part's failure becomes another part's symptom. Each link is marked observed or inferred; details and evidence in `docs/picapport-db.md` and the backlog.

1. **Stopping Picapport kills it mid-shutdown** (observed 2026-11-15). On `systemctl stop picapport-wrapper`, and so on every reboot or shutdown, Picapport starts its shutdown but has not exited after 30 s; systemd ends the init script's stop at 30 s (`TimeoutStopSec=30`) and SIGKILLs Java at 60 s, while Picapport's shutdown hook is still running. OrientDB itself allows 30 s to flush its write cache at shutdown. A power cut at the cable does the same, without any shutdown at all (Q3). **Change made (B10, 2026-11-15, on branch `feat/picapport-db-repair`):** `TimeoutStopSec=300` in the unit and `--retry=TERM/290/KILL/5` in the init script, synced by `update.sh`; how long a clean stop actually takes is not yet measured, and with the damaged database the shutdown may hang regardless.
2. **The database is left unclosed** (inferred from 1 and the `dirty.fl` flag) and pages can be left half-written. This is the strongest suspect for the repeated damage (Q11).
3. **A broken page puts the database in read-only mode** (observed in Picapport's log): `OPageIsBrokenException` names the page; since 2025-10-22 nothing new has been indexed (new photos, such as the honeymoon folder, never appear).
4. **The crawler keeps hitting the broken page** on every run (at start and at midnight), then `OLockException` once a minute for hours (observed; causal link inferred).
5. **The slideshow page fails** (observed): it plays right after a fresh Picapport start, then a JSON request fails (`PicApportJsonServlet ... InvocationTargetException`) and the page goes white or shows "Network Error", and does not recover by itself. That this is caused by 3 and 4 is a strong hypothesis (B03).
6. **Restarting `photo-api` takes Chromium down with it** (observed): Chromium runs in its cgroup. `update.sh` therefore relaunches the slideshow itself (B20).

Consequence for any fix: a repaired database will break again at the next stop or reboot unless step 1 is fixed first (B10, Q11).

## Photo API (port 3000, no authentication, LAN only)

| Endpoint | Behaviour |
|---|---|
| `GET /api/test` | Returns "Testing". Health check. |
| `GET /api/home` | Kills any Chromium and opens the Picapport home page in kiosk mode. |
| `GET /api/slideshow` | With **no** query string: replays the saved slideshow URL from `/var/lib/photo-api/slideshow_url.txt`; if that file is missing, empty or unreadable it uses the default (`q=noimagesfound`, interval 30). With **any** query string: builds `http://localhost:8080/picapport#slideshow?sort=random&autostart=true&viewtime=<interval>&query=<q>`, saves it there (a failure to save is logged and the slideshow still opens), and opens it. A missing `q` becomes `noimagesfound` and a missing `interval` becomes 30, so for example `?interval=10` overwrites the saved slideshow with `noimagesfound` (B17). |
| `GET /api/screen` | Toggles the monitor on/off with `vcgencmd display_power` (uses `sudo`). **Unverified** that this works under the current Wayland (labwc) desktop. |

Chromium is started with `pkill -9 chromium` first, so any running browser is killed. Flags include `--kiosk --start-fullscreen`.

**Restarting `photo-api` takes the slideshow off the screen** (observed on the Pi, 2026-11-15). Chromium is spawned by the API, so it runs inside `photo-api.service`'s cgroup (`KillMode=control-group`) and is killed when `photo-api` stops or restarts; the screen then shows the bare desktop. Nothing brings it back by itself: the API does not open Chromium when it starts, and `picapport-chromium.service` does **not** re-run (it is an inactive oneshot, and `PartOf=` only passes a restart on to units that are active). A `GET /api/slideshow` (no query string) brings the saved slideshow back. Since B20, `scripts/update.sh` restarts `photo-api` and then starts `picapport-chromium` itself on every update. (B06, B20)

## Known design issues (tracked in the backlog)

- ~~`api/slideshow_url.txt` was runtime state in a tracked file, so the Pi's checkout was always dirty.~~ Fixed in B06: the saved slideshow moved to `/var/lib/photo-api/`. Deployed to the Pi on 2026-11-15 (on `main`); the Pi's checkout is now clean apart from an untracked `api/package-lock.json`.
- Restarting `photo-api` by hand (outside `update.sh`) kills the slideshow and nothing relaunches it; start `picapport-chromium` or call `/api/slideshow` afterwards. (B20)
- Picapport's database is repeatedly corrupted (`OPageIsBrokenException`); a manual recovery procedure is in the README. (B03, B04)
- journald is configured `Storage=volatile`, so service logs are lost on every reboot. (B09)
- A leftover `~/.config/autostart/picapport-chromium.desktop` on the Pi (not from the repo) starts Chromium at `http://localhost:80`. (B12)
- The HDD is mounted read-write, and `scripts/mount-hdd.sh` picks the first non-SD partition that has a filesystem, so a second USB drive could be mounted instead. (L6, B16)
- The update path (`scripts/update.sh`, B06) is in use on the Pi since 2026-11-15: tested there for a branch, `main`, a rollback with `--ref` and the return to `main`. Not yet tested: `--discard-local-changes`, `--reset-slideshow`, a change that needs `npm install`. (B06, B15)
- `bootstrap.sh` does not yet use the shared install steps that `update.sh` uses (`scripts/lib/`); two code paths install units and config until bootstrap adopts them as part of the fresh-build test. (B11)
- The bootstrap has not been run on a blank Pi since September 2025. (B11)

## Updating the Pi (`scripts/update.sh`)

How a change reaches the Pi. Procedure: the `apply-changes` skill and README "Updating the Pi". Design facts:

- **Two phases.** Phase 1 (self-contained, so it can be piped over SSH before the Pi has it): checks the checkout is clean, `git ls-remote` and `git fetch`, resolves the target (`main`, `--branch`, `--ref`), prints the plan, then checks out (fast-forward only, or a detached checkout for `--ref`). Phase 2 is the **target commit's own** copy of the script, which applies it: state directory, `scripts/lib/apply-packages.sh` (installs packages listed in `config/packages.txt` that are missing; `apt-get update` only then, `--no-upgrade`; bootstrap installs the same list), `scripts/lib/apply-units.sh` (units and `/etc/init.d/picapport` that are already installed, `daemon-reload`), `scripts/lib/apply-extras.sh` (API `npm install` if `package.json` changed, Picapport properties, logrotate config and health-log cron entry, always), then restarts the app the way a boot starts it (`photo-api`, then `picapport-chromium`; every time, even if nothing changed), then verifies (services, HTTP codes, launcher result, Chromium running). `--dry-run` runs phase 2 from a temporary export of the target under `/tmp`, so a dry run previews the new logic without checking anything out.
- **Never done by the script:** upgrading or removing packages, reboot, touching `/mnt/photos` or `mount-hdd`, restarting Picapport (Q11), enabling or starting units that are not installed, `git reset`/`stash`/`rebase`.
- **Dirty checkouts.** It refuses tracked local changes, except executable-bit-only differences (git is run with `core.fileMode=false`, then the executable bits recorded in the repo are applied: `mount-hdd.service` runs `scripts/mount-hdd.sh` directly, so the bit matters) and `api/slideshow_url.txt`, which is accepted only if an identical copy is already in `/var/lib/photo-api/`; it is then moved there as `slideshow_url.txt.from-checkout-<time>`, not discarded.
- **Restarting the app, not the Pi** (owner decision 2026-11-15, B20). An update is finished when the app is running again the way a boot starts it, so every update exercises the boot start path for the API and the slideshow. Not restarted: `mount-hdd` (hard rule 1) and Picapport (Q11, until its stop is shown to be clean, B10). No reboot after an update. The health-log cron entry and the logrotate config are part of the app and always installed.
- **Testing the logic away from the Pi.** Paths and commands can be overridden by environment variables (`PI_REPO`, `STATE_DIR`, `LOG_DIR`, `UNIT_DIR`, `LOGROTATE_DIR`, `PICAPPORT_PROPS_DST`, `SYSTEMCTL`, `CURL`, `SUDO`, `APT_GET`, `DPKG_QUERY`; see `scripts/lib/common.sh`), which allows running it against a scratch clone with a stubbed `systemctl`. That tests the script logic only: it does **not** test `systemctl`, the real unit sync, `sudo`, file ownership or executable-bit handling (Windows git ignores modes), or Pi-specific behaviour.

## Picapport queries

What the photos carry, what Picapport indexes, and the query syntax are in [image-metadata.md](image-metadata.md) (layer 1, principle 12). Interfaces found (read-only, 2026-11-16):

- `GET http://localhost:8080/picapport_json?cmd=RunQuery&query=<q>&sort=random` (no login today) returns `status` (`OK`/`NORESULT`), `numPhotos` and a `vid` (server-side view id). This is the call the slideshow page makes; it does not touch Chromium or the saved slideshow. Whether `vid`s accumulate in memory is not known.
- `cmd=GetMetaData&vid=<vid>&index=<n>` (same cookie jar) returns one result's file name, dates, camera, GPS and `textSearch` (the indexed words).
- A query containing `*` makes `picapport_json` fail with HTTP 500. Never send one.
- Picapport's documented Web API (`/picapportapi/1.0/runQuery`, wiki 2019) answers 404 here; `picapport.properties` has no `webapi` settings. Whether enabling it would be better for the photo API than `picapport_json` is open (B24, phase 3).

## Picapport slideshow behaviour that matters (from Picapport 10.4.0's page code, and tested)

- **Order.** The slideshow page runs one `RunQuery` with `sort=random`, then plays index 0, 1, 2, ... of that result and wraps to 0 at the end. **The shuffle is a true shuffle** (tested 2026-11-16: the 1,916 Noosa photos gave 1,916 distinct files, and a second run a different order with 1 photo in the same place). So a photo repeats only after the whole result has played (11,807 honeymoon photos at 20 s is about 65 hours), **or after a relaunch**, which reshuffles: every boot, every `update.sh` and every `/api/slideshow` call. Two shuffles overlap quickly (watching 1,000 of 10,000 photos from each gives about 100 repeats). The API log showed 14 relaunches on 2026-11-15 (maintenance) against about one a day in normal use (B26).
- **Failures.** The page asks the server for data with JSON calls. If one fails, the page goes into an offline state and shows the dialog "Network Error. Info: Not connected. Verify Network."; it does not retry by itself. See backlog B03.
